# Правила работы в NotesBot

## Контекст и границы

- Это Telegram-бот для текстовых заметок. Требования: [docs/mvp.md](docs/mvp.md); схема: [docs/architecture.md](docs/architecture.md).
- Порядок развития: [docs/roadmap.md](docs/roadmap.md); шаги выбранного пункта: [docs/plan.md](docs/plan.md); текущее состояние, результаты и границы поручения: [docs/progress.md](docs/progress.md). Перед работой прочитать эти документы.
- Здесь хранить постоянные правила, а состояние проекта и результаты этапов обновлять в `docs/progress.md`. Наличие roadmap или плана не разрешает начинать реализацию без поручения.
- Прочитать инструкции проекта и документы, относящиеся к текущей задаче. Описать границы изменений; выполнять только порученный этап, не переходить ко всему MVP автоматически.
- Обсуждение и итоговый отчёт вести по-русски. Имена Python-модулей, функций и переменных — по-английски.
- При расхождении документов сообщить о нём; явные указания пользователя имеют приоритет над локальными workflow. Не запрашивать повторное разрешение на уже порученные действия.

## Git и пользовательские изменения

- Перед изменениями проверить ветку, рабочее дерево и staging. Сохранять существующие пользовательские изменения; не сбрасывать и не переписывать их.
- Рабочая ветка — `develop`. В `main` не вести разработку. Если активна другая ветка, сообщить об этом и не переключаться с пользовательскими изменениями без проверки.
- Менять только файлы текущей задачи. Не менять staging, не создавать commit, не делать merge и не отправлять изменения без отдельного поручения.
- Skills не дают разрешения на Git-операции; рекомендации о частых коммитах не отменяют это правило.

## Код и данные

- Стек и границы модулей определены в документах MVP. Telegram-обработчики и хранение должны оставаться независимыми; не вводить новую библиотеку, слой или общую абстракцию ради локальной задачи.
- Следовать настройкам форматирования и ближайшему коду той же роли. При изменении контракта проверять непосредственных потребителей и соответствующие тесты.
- Для чтения, поиска и удаления обязательно ограничение по `user_id` отправителя; SQL только с параметрами. Подтверждать запись или удаление после успешной операции хранения.
- Не помещать секреты, ключи, signing data, локальные настройки машины, реальные заметки и БД в отслеживаемые файлы, логи или отчёты. Не читать содержимое `.env` и реальные данные ради обычного ревью.
- Для проверок использовать вымышленные данные и временную файловую SQLite-БД; обработчики проверять без настоящего Telegram API.

## Сборка и проверки

- В этом проекте пользователь разрешил и требует после изменений Python-кода, тестов, зависимостей или конфигурации сборки проверять компиляцию, запускать весь набор тестов и собирать пакет. Это проектное исключение из общего пользовательского запрета; дополнительное согласование этих проверок не требуется, в том числе для тестов с компиляцией.
- В подготовленном окружении проекта с Python 3.12+ выполнять из корня: `.venv/bin/python -m compileall -q notes_bot tests`, `.venv/bin/python -m pytest -q`, `uv build --no-build-isolation`. Для сборки использовать заранее установленные build-зависимости; не устанавливать их автоматически.
- При изменении только документации, инструкций агентов или `.gitignore` достаточно проверки diff, текста, ссылок и конфигурации. Если изменены исполняемые скрипты или параметры сборки/тестов, выполнить соответствующие проверки кода.
- Не устанавливать зависимости и не запускать реального бота с сетью без отдельного разрешения. Не использовать `uv run` как способ незаметно создать окружение или установить пакеты.
- Во время работы допустим запуск отдельных затронутых тестов; перед завершением изменения кода обязательны весь набор тестов, проверка компиляции и сборка. Сообщать команды и результаты; исправлять выявленные проблемы в границах задачи и повторять затронутые проверки.
- Если код, тесты, `pyproject.toml`, окружение или инструмент ещё отсутствуют, сообщить, какие проверки не выполнены и почему. Не создавать каркас и не устанавливать инструменты лишь ради проверки документации; не называть проверку полной и не заявлять об успехе невыполненных команд.

## Навыки и rules

- Локальные навыки находятся в `.agents/skills`: `notes-task` для выполнения одного порученного этапа; `notes-review` для ревью. Загружать только относящийся к запросу навык.
- Делегирование применять по запросу пользователя или когда его явно требует применимый skill. Для обычной разработки по умолчанию работать последовательно в текущем чате.
- Постоянные правила поведения хранятся здесь. `.codex/rules/notes-bot.rules` содержит дополнительные подтверждения команд вне sandbox; разрешение проверок в `AGENTS.md` не отменяет ограничения sandbox и подтверждения команд Codex.
- Инструкция по использованию и ограничения: [docs/agent-workflow.md](docs/agent-workflow.md).

## Code Review Rules

- Отмечать как дефект доступ к чужим заметкам, SQL-интерполяцию, раскрытие секретов или реальных заметок, потерю текста и ложное подтверждение сохранения/удаления.
- Проверять кириллицу и буквальные `%`/`_` в поиске, порядок последних 10 заметок, ошибочные команды, личные и групповые чаты, длинные ответы с emoji.
- Проверять, что синхронный SQLite не блокирует event loop и соединение не переносится между потоками.

## Завершение

- Просмотреть итоговый diff, включая новые файлы; убедиться, что изменения ограничены задачей и staging сохранён, если его изменение не поручалось.
- Сообщить, что изменено, какие проверки выполнены, какие не выполнены и какие вопросы остаются открытыми.
