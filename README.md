# NotesBot

Telegram-бот для сохранения, просмотра, поиска и удаления текстовых заметок.

Требования: [MVP](docs/mvp.md), [архитектура](docs/architecture.md).
Порядок развития: [roadmap](docs/roadmap.md), шаги выбранного пункта:
[plan](docs/plan.md), текущее состояние: [progress](docs/progress.md).

## Подготовка окружения

Нужны Python 3.12+ и uv. Если uv уже установлен, использовать его. Для локальной
установки инструментов внутри проекта на macOS/Linux выполнить из корня:

```sh
python3 -m pip install --target .tools/uv --only-binary=:all: 'uv==0.13.1'
export PATH="$PWD/.tools/uv/bin:$PATH"
export UV_CACHE_DIR="$PWD/.uv-cache"
export UV_PYTHON_INSTALL_DIR="$PWD/.python"
uv python install 3.12 --no-bin
uv sync --locked --python 3.12 --no-install-project
```

`export` действует только в текущем shell. После открытия нового терминала
повторить три команды `export` из корня проекта. Python установлен в `.python/`,
инструменты в `.tools/`, зависимости в `.venv/`; эти каталоги исключены из Git.
`--no-install-project` устанавливает зависимости без установки самого NotesBot.
Версии зависимостей зафиксированы в `uv.lock`.

## Настройки

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `BOT_TOKEN` | Токен Telegram-бота; обязателен и не может быть пустым | Нет |
| `DATABASE_PATH` | Непустой путь к файлу SQLite | `data/notes.sqlite3` |

Пример передачи настроек в текущий shell:

```sh
export BOT_TOKEN='replace-with-your-telegram-bot-token'
export DATABASE_PATH='data/notes.sqlite3'
```

Локальный `.env` исключён из Git. Приложение не читает его автоматически.
Реальный токен не помещать в отслеживаемые файлы, команды для
публикации, логи или отчёты. `load_settings()` проверяет наличие токена; проверка
его подлинности через Telegram в этот этап не входит.

## Проверки

Из корня проекта с подготовленным окружением:

```sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python -m compileall -q notes_bot tests
.venv/bin/python -m pytest -q
uv build --no-build-isolation
```

Если uv установлен локально и отсутствует в PATH, для сборки выполнить
`UV_CACHE_DIR="$PWD/.uv-cache" .tools/uv/bin/uv build --no-build-isolation`.
В конфигурации pytest корневой `.env` явно исключён из обхода: файловый
запрет доступа действует и при проверке типа файла, ещё до чтения содержимого.

Сборка создаёт sdist и wheel в `dist/`, используя build backend `uv_build`,
установленный вместе с dev-зависимостями. Тесты настроек используют вымышленные
значения и не обращаются к Telegram.

## Как агент работает в проекте

Перед работой агент читает [AGENTS.md](AGENTS.md), [требования MVP](docs/mvp.md),
[архитектуру](docs/architecture.md), [roadmap](docs/roadmap.md),
[план выбранного этапа](docs/plan.md) и [текущее состояние](docs/progress.md).
Затем изучает относящиеся к поручению файлы и проверяет ветку, рабочее дерево
и staging. Наличие плана не разрешает начинать следующий этап автоматически.

По задаче агент использует один из локальных навыков:

- [notes-task](.agents/skills/notes-task/SKILL.md) — реализация одного порученного этапа MVP.
- [notes-review](.agents/skills/notes-review/SKILL.md) — ревью изменений без автоматических исправлений.

Рабочая ветка — `develop`. Агент может читать разрешённые файлы, менять файлы
порученной задачи и выполнять предусмотренные проектом проверки. Он сохраняет
пользовательские изменения. Изменение staging, commit, merge, push, установка
зависимостей и запуск настоящего бота с сетью требуют отдельного поручения
или разрешения. Читать `.env` любыми инструментами запрещено; реальные заметки
и БД не используются при обычном ревью. Для проверок нужны вымышленные данные.

Работу страхуют следующие проверки и ограничения:

- Хук [.codex/hooks.json](.codex/hooks.json) после каждой правки `.py` через
  `apply_patch` запускает Ruff format и check для затронутых файлов.
  Хук требует доверенного проекта и подтверждения пользователем; если он
  не сработал или применён другой инструмент, агент запускает команды вручную.
- Перед завершением изменения Python агент проверяет линтер и формат всего
  проекта, компиляцию, весь набор тестов и сборку пакета командами из раздела
  «Проверки». Для изменений только документации достаточно проверки текста,
  ссылок и diff. Недоступные проверки указываются в отчёте.
- [.codex/rules/notes-bot.rules](.codex/rules/notes-bot.rules) задаёт дополнительные
  подтверждения команд и запреты некоторых прямых команд чтения `.env`.
  Эти запреты не охватывают все способы чтения файла. Sandbox ограничивает доступ инструментов согласно
  активной конфигурации. Правила в `AGENTS.md` сами по себе не блокируют чтение файлов.
- [.codex/config.toml](.codex/config.toml) выбирает профиль `notes-bot` с файловым
  `deny` для корневого `.env`. Для локальных команд он блокирует чтение и запись
  файла внутри sandbox. Нужны доверенный проект и перезапуск Codex без старых
  настроек `sandbox_mode` / `--sandbox`; MCP и внешние приложения имеют отдельные права.
- Агент просматривает итоговый diff, проверяет `git diff --check` и записывает
  результат, команды проверок и ограничения в [progress](docs/progress.md).

Чтобы запустить весь набор тестов, из корня проекта с уже подготовленным
окружением выполните:

```sh
.venv/bin/python -m pytest -q
```

Тесты не требуют настоящего токена или запуска бота. Подробности работы агента
и активации хука — в [agent-workflow](docs/agent-workflow.md).
