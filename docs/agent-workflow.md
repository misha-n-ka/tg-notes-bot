# Инструкции для агентов

## Что где хранится

| Файл | Назначение |
|---|---|
| `AGENTS.md` | Постоянные правила проекта: Git, сборка, данные, границы MVP |
| `docs/roadmap.md` | Верхнеуровневый порядок развития проекта |
| `docs/plan.md` | Шаги реализации одного выбранного пункта roadmap |
| `docs/progress.md` | Текущее состояние, результаты проверок и границы поручения |
| `.agents/skills/notes-task/SKILL.md` | Повторяемый workflow одного порученного этапа реализации |
| `.agents/skills/notes-review/SKILL.md` | Ревью изменения с проверкой поведения и непосредственных потребителей |
| `.agents/skills/notes-rules-check/SKILL.md` | Проверка совпадений `.rules` без выполнения целевых команд |
| `.codex/rules/notes-bot.rules` | Разрешения, запреты и подтверждения отдельных команд вне sandbox |
| `.codex/config.toml` | Профиль разрешений `notes-bot` с файловым запретом доступа к `.env` |
| `.codex/hooks.json` | Автоматическое форматирование и линтер после правок Python через `apply_patch` |
| `.codex/hooks/ruff_after_edit.py` | Запуск Ruff для Python-файлов текущей правки |

Требования продукта не копируются в навыки: источник — `docs/mvp.md`. Roadmap описывает этапы, plan — шаги выбранного этапа; сами по себе они не разрешают выполнение. Перед работой читать progress, после работы обновлять результаты в нём. Проверка компиляции, весь набор тестов и сборка после изменений кода разрешены пользователем и обязательны по `AGENTS.md`; навыки наследуют это правило.

## Примеры запросов

- «Используй $notes-task. Реализуй только задачу 2 из плана и выполни проверки по AGENTS.md». Использовать после возобновления реализации.
- «Используй $notes-review. Проверь текущие изменения без исправлений и сборки».
- «Проверь правила команд для private/demo.txt и соседнего public/demo.txt» — автоматический выбор `notes-rules-check`; бизнес-правила бота к нему не относятся.
- «Проверь AGENTS.md и локальные skills на противоречия» — это настройка инструкций, а не задача реализации бота.

Навыки имеют узкие описания для автоматического выбора. Если новый навык ещё не виден в текущем чате, можно указать путь к его `SKILL.md`; при необходимости начать новый чат в этом проекте.

## Хук Ruff

После каждого `apply_patch` хук форматирует существующие `.py` файлы из этой
правки и проверяет их линтером. Используется `.venv/bin/ruff` с настройками
`pyproject.toml`. Ошибки возвращаются агенту; зависимости не устанавливаются.
Удалённые файлы и пути за пределами проекта пропускаются. Правки через shell,
MCP или внешний редактор этот хук не отслеживает; ручной запуск для правок
агентом обязателен по `AGENTS.md`.

Для активации проектный слой `.codex` должен быть доверенным, а определение хука
проверено и подтверждено пользователем. В CLI это выполняется через `/hooks`.
После изменения определения хука требуется повторное подтверждение. До активации
агент выполняет команды вручную. Итоговые проверки всего проекта остаются
обязательными по `AGENTS.md`.

## Файловый запрет доступа к `.env`

В `.codex/config.toml` выбран `default_permissions = "notes-bot"`. Профиль
наследует `:workspace`, сохраняя его ограничения, и задаёт `.env = "deny"`
в таблице `permissions.notes-bot.filesystem.":workspace_roots"`.
Это запрещает чтение и запись корневого `.env` каждого активного workspace root
локальными командами внутри sandbox, в том числе через Python.

Для применения нужен доверенный проектный слой `.codex` и перезапуск Codex.
Не совмещать профиль с `sandbox_mode`, `sandbox_workspace_write` или запуском
с `--sandbox`: старые настройки sandbox могут подменить выбранный профиль.
Уже работающая сессия не получает новый профиль автоматически.

Для проверки действующей защиты сначала изучить эффективную политику текущего
чата: явный неэскалируемый `deny` подтверждает наличие файлового ограничения
без чтения файла. Имя профиля само по себе из эффективной политики не следует.
pytest настроен пропускать `.env` при сборе тестов, поскольку запрет блокирует
даже проверку типа этого файла.

Проверка на временном вымышленном `.env` через `codex sandbox -P notes-bot`
подтвердила отказ чтения при сохранении чтения и записи обычных файлов.
Настоящий `.env` для проверки не открывался. Профиль ограничивает локальные
команды в sandbox; MCP, внешние приложения и разрешённые escalation имеют
отдельные механизмы доступа. Агенту запрещено использовать их для обхода.

Описание механизма: [официальная документация Permissions](https://learn.chatgpt.com/docs/permissions).

## Ограничения rules

Правила используют `decision = "prompt"` для подтверждений и `forbidden` для
прямого чтения `.env` командами `cat`, `head`, `tail`, `less`, `more`, `bat`
и загрузки через `source` или `.`. Запрет сопоставляет `.env` и `./.env`
первым аргументом; для команд чтения также поддержан вариант с `--`.
Добавлены `allow` для `ruff check`, `ruff format --check` (включая
`.venv/bin/ruff`), `.venv/bin/python -m pytest`, `pytest` и `.venv/bin/pytest`.
Для Git разрешены `status`, `diff`, `log`, `show`, `ls-files` и
`branch --show-current`. Это префиксы команд: разрешение `ruff check` включает
его дополнительные опции, в том числе `--fix`. Обычный `ruff format` без
`--check` этими правилами не разрешён.

Пользователь уже разрешил компиляцию, тесты и сборку после изменений кода;
подтверждение выхода команды за пределы sandbox может по-прежнему потребоваться
для команд вне списка `allow` или при более строгой активной политике.
Для commit, push, установки зависимостей или приложения и реального запуска
бота необходимо отдельное поручение. `uv run` сохраняет `prompt`, поскольку
может установить зависимости.

Проектные `.rules` загружаются при старте Codex только из доверенного слоя `.codex`. Текущую сессию нельзя считать защищённой новыми rules автоматически. Перед использованием проверить доверие проекту и перезапустить Codex; настройки доверия и глобальные настройки этим изменением не меняются.

Проверка файла без выполнения целевой команды:

```sh
codex execpolicy check --pretty --rules .codex/rules/notes-bot.rules -- uv sync
codex execpolicy check --pretty --rules .codex/rules/notes-bot.rules -- git commit -m example
codex execpolicy check --pretty --rules .codex/rules/notes-bot.rules -- git status --short
codex execpolicy check --pretty --rules .codex/rules/notes-bot.rules -- cat .env
```

Для первых двух команд ожидается `prompt`; для `git status` — `allow`.
Для `cat .env` ожидается `forbidden`; проверка политики не выполняет саму команду.
Другие активные политики могут дать более строгое решение.

Эти запреты не закрывают чтение через Python, MCP, перенаправления shell,
абсолютные пути, дополнительные опции или другой порядок аргументов. Для полного
запрета локальных команд используется профиль с `deny` из `.codex/config.toml`.

Rules сопоставляют префиксы команд и не охватывают все обёртки и варианты вызова.
Абсолютный путь к инструменту или опции перед подкомандой могут не совпасть с
разрешённым префиксом. `AGENTS.md` определяет обязательные проверки; rules и
sandbox отдельно контролируют выполнение команд. `allow` снимает подтверждение
для совпавшей команды вне sandbox, если нет более строгой политики.

## Проверка навыков

При изменении навыка проверить YAML-поля `name` и `description`, ссылки и отсутствие шаблонных заглушек. Затем проверить его на реалистичном запросе с вымышленными данными без изменения кода проекта. Структурная проверка не доказывает качество поведения; фиксировать выполненные сценарии и ограничения в отчёте.

Начальная проверка 13 октября 2026 года:

- `notes-task`: до загрузки навыка в поручение «только сохранение» попало чтение списка из общего пункта плана. После загрузки область ограничилась записью и необходимой инициализацией. Запрос настройки skills не был принят за возобновление реализации.
- `notes-review`: на словесном примере обнаружены удаление без ограничения владельцем, неверная обработка кириллицы и символов `%`/`_`, ложное подтверждение удаления. Агент обозначил отсутствие реального кода и тестов, не придумал номера строк и не выполнил исправления.
- YAML проверен системным Ruby/Psych; имена, поля и ссылки проверены отдельно. Штатный `quick_validate.py` не запустился из-за отсутствующего PyYAML, зависимости не устанавливались.

Это проверка начальной версии на двух сценариях, не гарантия поведения агента во всех запросах. На момент той проверки код бота отсутствовал, его тесты и сборка не запускались. Актуальное состояние — в [progress.md](progress.md).
